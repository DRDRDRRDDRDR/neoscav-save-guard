# NEO Scavenger 存档守护 —— 中文使用说明

本文是 README 的详细中文补充，面向日常使用与故障排查。
英文版（主文档）见 [USAGE.md](USAGE.md)。

---

## 一、它会自动做什么

监视器每 10 秒检查一次，命中以下任一条件就立刻备份一份带时间戳的快照：

1. **检测到 `NEOScavenger.exe` 进程启动**
   → 把当前存档快照一份（等于"一开游戏就自动备份一次"）
2. **检测到 `nsSGv1.sol` 内容发生变化**
   → 立刻快照一份（等于游戏里 Quit and Save 之后自动备份）
3. **启动游戏时顺带自动打开回档器界面**
   → 不用再自己去双击图标；一次启动只拉起一次，不会重复弹窗
   → 若回档器本来就开着，则把那个窗口切到前面（不会开出第二个）

因此无论你是从 Steam、桌面还是任何方式启动游戏，都会生效 ——
它监视的是文件与进程，和启动入口无关。

## 二、回档：图形界面

**开游戏时会自动打开**，通常不必手动点。需要手动打开时，双击：

```
save_rollback_gui.pyw
```

（重复打开不会出现两个窗口：程序用命名互斥量做单实例保护，
若已在运行，会把原窗口切到最前面并退出。）

界面功能：

- 列出全部快照（时间 / 大小 / 触发原因 / 完整性），第一项就是"死前最后一份"
- **【完整】列**校验 `.sol` 头部结构：损坏的会标红，并且**拒绝回档**
- 【回档为当前存档】把选中的快照还原成 `nsSGv1.sol`（双击列表项同效）
- 【存入槽1/2/3】把快照写进 NEO Save Manager 的命名槽
- 【存入Quicksave槽】写进 `g0`，之后在工具里读回
- 【打开备份文件夹】【刷新】【重启监视器】

回档后：启动游戏 → 主菜单选 Continue → 接着那份进度继续。

### 三条安全机制

1. **游戏正在运行时拒绝回档。** Flash 把存档握在内存里，游戏退出时会用内存内容
   覆盖 `nsSGv1.sol`，此时回档会被抹掉，而用户只会以为"回档没用"。
   界面上会问你是否结束游戏进程，确认后才继续。
2. **覆盖前自动把"当前存档"另存为 `*_prerestore.sol`**，
   所以连"回档"这个动作本身也可以再回退。
3. **回档前校验 `.sol` 头部结构**（魔数 `00 BF` + 长度字段 == 文件大小 − 6）。
   被截断的快照会被拦下 —— 否则游戏会读不出存档，
   而现象只是"回档了但游戏打不开"，很难定位。

### 命令行等价用法

```
save_rollback_gui.pyw --list                          列出所有快照
save_rollback_gui.pyw --restore latest --yes          回档到最新一份
save_rollback_gui.pyw --restore 3 --yes               回档到列表中第 3 份
save_rollback_gui.pyw --restore-slot 2                把最新快照写入槽 2
save_rollback_gui.pyw --status                        查看状态
```

> 命令行要用**含 tkinter 的 Python** 运行；GUI 模式不加参数双击即可
> （`.pyw` 已关联 `pyw.exe`，不弹黑框）。
>
> **界面语言**：默认英文。想要中文界面，设 `NSG_LANG=zh` 环境变量，
> 或在 `config.json` 里写 `{"lang": "zh"}`。详见 README 的「界面语言」一节。
> 注：旧版文件名 `存档回档器.pyw` 仍被监视器识别，从 v1.0.0 迁移的部署无需改动。

## 三、备份存在哪里

默认备份目录：

```
<用户文档>\NEO Scavenger Save Guard\auto\
  nsSGv1_YYYYmmdd-HHMMSS_save.sol        存档变化触发的快照
  nsSGv1_YYYYmmdd-HHMMSS_start.sol       游戏启动触发的快照
  nsSGv1_YYYYmmdd-HHMMSS_prerestore.sol  回档前自动留的底
  watcher_state.json                     运行状态
  watcher.log                            运行日志（超过 1 MB 自动滚动）
```

该目录在游戏安装目录之外，所以游戏内工具菜单里的
`D) Delete ALL saves!` 和 `W) Wipe NEOScavenger data!` 都删不到它。

若检测到 `<游戏目录>\NSM\`，最新快照还会同步刷新到该目录下的 Quicksave 槽
（`nsSGv1_g0.sol`）。目录不存在时这一步自动跳过。

## 四、保留策略（按时间分层）

```
最近 2 小时        逐份全留
2 小时 ~ 48 小时   每小时留 1 份
超过 48 小时       每天留 1 份
硬上限            600 份 / 300 MB（超了丢最旧的）
```

单份快照约等于当前存档大小（随进度增长，实测 1.3 ~ 1.8 MB）。

## 五、日常管理命令

在本工具目录下：

```bat
python autobackup_setup.py status      查看任务/进程/快照/槽位
python autobackup_setup.py run         手动跑一轮（立即备份一次）
python autobackup_setup.py seed        把最新快照写进槽1 + 槽0
python autobackup_setup.py restart     改过 neo_save_watcher.py 后重启生效
python autobackup_setup.py uninstall   停用并删除计划任务（备份保留）
python autobackup_setup.py install     重新启用
```

也可用 Windows「任务计划程序」图形界面管理同名任务。

## 六、故障排查

### 是否在运行

`auto\watcher_state.json` 每 10 秒被重写一次，看它的修改时间即可。
或 `python autobackup_setup.py status`。

### 没反应

1. 计划任务存在且状态为"已启用"
2. `pythonw.exe` 存在（本工具取自"当前运行脚本的解释器"同目录；
   若卸载或升级过 Python 导致路径变化，重新执行 `install` 即可重建任务）
3. 看 `auto\watcher.log` 最后几行

### 日志出现 `read_stable 失败`

读存档时文件恰好一直变化（游戏正在写盘）。这是保护机制 ——
宁可跳过这一轮，也不写一份可能损坏的快照。下轮自动重试。

### 存档路径变了

重装游戏 / 换 Steam 库 / `%APPDATA%` 变动都会让路径变化。
正常情况下自动探测会跟上；若没有，运行 `--check` 看解析结果，
再把 `config.json` 里的 `save_dir` 显式填上。

## 七、为什么这样设计（踩过的坑）

### 坑 1：给快照加"冷却"是有害的 —— 已用真实事故证伪

最初给快照加了 30 秒冷却，理由是"游戏会周期性写盘，每变化一次就存一份会刷爆快照"。
**这个推理是错的**，因为它默认"被推迟的快照以后还能补上"。实测日志：

```
17:01:44  快照 200,996 B（死亡前最后一份，可用）
17:02:04  检测到 198,511 B，但距上次快照仅 21 秒 < 30 秒冷却，被推迟
17:02:14  存档文件消失（角色死亡，游戏删档）
```

该状态**永久丢失**，只能回退到 `17:01:44`。

**正确做法：不设冷却。** 磁盘风险改由时间分层保留 + 总量硬上限控制。
一般规律：**凡是"推迟执行"的优化，都要问一句「如果目标在推迟窗口内消失了会怎样」**。

### 坑 2：存档缺失时日志刷屏

存档被删除后，监视器每 10 秒记一行"存档不可读"，10 分钟就是 60 行，把日志淹掉。
改为**只在状态翻转时记一次**（缺失记一次、恢复记一次）。

### 坑 3：只有浏览器走代理时的进程检测

进程检测使用 Win32 Toolhelp32 快照按 **exe 名**匹配，不依赖 `wmic` 的文本输出 ——
`wmic` 输出是 GBK，脚本名含中文时会解码错误，导致判定"进程不存在"。
同理，验证"GUI 真的建出来了"要用与编码无关的证据（命名互斥量 + 窗口句柄 + PID 反查），
而不是去匹配命令行文本。

### 坑 4：部署 ≠ 改完文件

改过 `neo_save_watcher.py` 后**必须** `python autobackup_setup.py restart`。
判断生效与否不要只看文件修改时间，要同时看**进程启动时间**和**启动横幅字段** ——
横幅会打印解析出的路径与功能开关（如 `带起GUI=True`）。

## 八、这套机制存在的理由

在还没有任何备份机制时，一次死亡让存档被游戏删除，数据随即被 NVMe SSD 的 TRIM
物理抹零，用 NTFS 底层取证确认为**不可恢复**。

这类"死亡即删档"的游戏，备份机制的**唯一价值点**就是抓住"死前最后一次存档"。
任何会推迟快照的优化，都是在拿这个价值点冒险。
